# Naukri.com browser automation bot (greenfield)

A Playwright-based CLI tool that automates job applications on Naukri.com. Given a list of URLs, it navigates to each listing, extracts metadata (title, company, location), determines whether the job uses Naukri's "Easy Apply" or redirects to an external ATS, and attempts to submit an application through either path. Results are logged to CSV in real-time.

The architecture splits cleanly into layers: Pydantic models and config at the bottom, a browser session manager in the middle, and three application strategies (applicator detection, easy-apply handler, external-apply handler) on top, all wired through a Click CLI. The form-filling layer uses pattern-based selector matching across multiple field types.

**Watch for:** hardcoded password in external signup forms (confirmed), credentials loaded at module import time via `load_dotenv()` at module level (confirmed), no rate limiting or backoff between applications (confirmed), and broad exception swallowing throughout the automation layer that will make production debugging difficult (confirmed).

## High-level view

The configuration system uses a two-layer approach (YAML + env vars) with Pydantic validation, but `load_dotenv()` fires at import time of `config.py` rather than at point of use, meaning any import of the config module has the side effect of loading `.env` into the process environment. Credentials flow through the config object but one code path in `external_apply.py` hardcodes a plaintext password for signup forms, bypassing the config entirely.

Form interaction across both apply paths relies on cascading selector lists with broad exception catching. When selectors miss (and they will, given Naukri's frequent DOM changes), every failure is silently swallowed, making it impossible to distinguish "field not present on this page" from "our selector is stale." The tool will degrade from working to silently failing without any signal.

The apply-type detection logic in `applicator.py` has a fallthrough that classifies nearly everything as EASY_APPLY. If the `href` check doesn't catch an external redirect, the tool will attempt Naukri's Easy Apply flow on a page that has already navigated away.

The test suite covers models, config loading, CSV logging, and metadata extraction thoroughly, but does not test the easy-apply handler, the external-apply handler's form-filling logic, or the CLI's orchestration loop. The most complex and fragile code paths have zero test coverage.

## Hardcoded credential in external signup flow

In `external_apply.py`, the `_fill_signup_form` method fills password fields with a hardcoded string:

```python
async def _fill_signup_form(self, page: Page) -> None:
    profile = self._config.user_profile
    email_field = await find_field(page, "email")
    if email_field:
        await fill_text_field(email_field, profile.email)
    password_field = await find_field(page, "password")
    if password_field:
        await fill_text_field(password_field, "AutoApply2024!")
```

This creates an account on an external ATS with a credential the user doesn't control or know about. It's both a security concern (the password is in version control) and a usability problem (the user can't recover these accounts). If the signup-filling behavior is intentional, the password should come from config. If not, this path should be removed or gated behind an explicit opt-in flag.

## `load_dotenv()` at import time

```python
# config.py top-level
from dotenv import load_dotenv
load_dotenv()
```

This means `import naukri_apply.config` has the side effect of reading `.env` and injecting values into `os.environ`. In testing, this can leak state between test modules. In production, it means the `.env` file must exist (or not raise) at any point the config module is transitively imported.

## Apply-type detection falls through to EASY_APPLY

The `_determine_apply_type` method in `applicator.py` has this logic:

```python
text = await apply_button.text_content()
if text:
    lower_text = text.lower()
    if "easy apply" in lower_text or "apply on company" not in lower_text:
        return ApplyType.EASY_APPLY
return ApplyType.EASY_APPLY
```

The condition `"apply on company" not in lower_text` is true for virtually any button text that isn't specifically "Apply on Company Site." This means buttons labeled "View Details," "Save," or any other text will be classified as EASY_APPLY. The final fallback `return ApplyType.EASY_APPLY` means the method can never return EXTERNAL unless the `href` explicitly points off-domain. If Naukri changes their external-redirect pattern to use JavaScript navigation instead of an `href` attribute, all external jobs will be misclassified.

## No rate limiting or backoff

`_run_apply` iterates URLs sequentially with no delay:

```python
for i, url in enumerate(urls, 1):
    # immediately processes next URL after previous completes
```

Naukri.com and external ATS platforms will flag rapid sequential requests from the same session. A configurable delay between applications (even 5-10 seconds) would substantially reduce the risk of account suspension.

## Silent exception handling makes failure invisible

Every selector-cascade method follows this pattern:

```python
for selector in selectors:
    try:
        element = self._page.locator(selector).first
        if await element.is_visible(timeout=3000):
            text = await element.text_content()
            if text and text.strip():
                return text.strip()
    except Exception:
        continue
return "Unknown"
```

When Naukri updates their DOM (which happens frequently for Indian job portals), the tool will return "Unknown" for all metadata fields and likely fail to find apply buttons. The user sees "Unknown" in their CSV but has no way to know whether the selector list needs updating without manually debugging. At minimum, the `except Exception` blocks should log at DEBUG level so users can enable verbose output to diagnose failures.

## Test coverage gaps

Not tested:
- `EasyApplyHandler.apply()` — the entire screening-question logic, success detection, and failure modes
- `ExternalApplyHandler.apply()` — new-tab detection, platform detection, signup vs. application form branching, form submission
- `BrowserManager` — context creation, login detection, page lifecycle
- `main.py` CLI orchestration — URL file parsing, error continuation, summary output
- Integration between components (applicator result flowing into handler selection)

The untested code is the most fragile and the most likely to break when Naukri's UI changes.

## External apply new-tab detection fragility

`ExternalApplyHandler._click_apply_and_get_new_page` first tries `context.expect_page` with a 10-second timeout. If no new page event fires (e.g., the external site opens in the same tab via JavaScript redirect), it falls back to clicking without the page listener. But the fallback loop re-iterates the same selectors — if the first loop already clicked a button that navigated the current page, the second loop will be trying selectors on the external site's DOM rather than Naukri's. This won't crash (the selectors just won't match), but it wastes 15+ seconds of timeout per selector before returning `None`.
